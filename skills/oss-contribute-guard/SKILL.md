# 开源贡献避坑核对（oss-contribute-guard）

给外部开源仓库做贡献时的核对清单与流程规范。本 skill 是**行动前强制核对**性质的：每个关键动作（fork 同步、认领、commit、推 PR、关 PR、回复评审）执行前先过对应核对项，全部通过才执行。

## 触发场景

- 用户提到给某个开源仓库提 PR / issue / 认领 issue
- 回复开源仓库维护者的评审意见
- 处理开源 PR 的 CI 失败、冲突、回归质疑
- 在 fork 上同步上游、重置分支

## 身份与环境铁律

1. **提交身份统一**：`git -c user.name=lnuxe -c user.email=144079529+lnuxe@users.noreply.github.com commit`，不依赖全局配置
2. **远程命名**：`origin` = 自己 fork（lnuxe），`upstream` = 上游官方仓库；推送只推 origin
3. **fork 与上游同源检查**：动手前 `git fetch upstream && git diff upstream/develop --stat` 确认零差异；有分叉历史时宁可强制同步重放提交，也不要带着历史包袱提 PR
4. **分支命名**：`feat/`、`fix/`、`perf/`、`docs/` + 短语义名（如 `perf/indexes-lazy-content`），一律小写 kebab

## 认领 issue 流程（严格按序）

1. **读上游 CONTRIBUTING.md**：不同仓库规则差异大，不可凭经验跳步
2. **打标签**：确认 issue 是否需要 `issueShoot` 类标签（部分仓库要求维护者打标后才可认领）
3. **留言认领 + 打 `Received`**：认领时说明方案方向，附初步调研证据
4. **等维护者确认方案后再开发**：不要抢跑实现——方案被否时沉没成本极高
5. **认领前核对上游最新代码**：旧 issue 很可能已被重构顺带解决，先在上游 develop 分支验证问题是否仍存在，再决定是否认领

## 提 PR 规范

1. **PR 必须保留完整模板**：仓库 PR 模板的 HTML 注释和勾选清单（如 tdesign-flutter 的 11 项 checklist）必须原样保留并逐项勾选，删模板会被直接打回
2. **正文结构**：问题描述 → 方案说明 → 测试证据（截图/数据）→ spec 引用；性能类 PR 必须附改造前后对照数据
3. **spec 变更同 PR 提交**：组件仓库若有 specs/ 目录，API 变更需在同一个 PR 里补 record，不能事后补
4. **截图证据**：真机验证截图存 `specs/components/<组件>/` 或 PR 描述 raw 链接，保证评审者可查
5. **单 PR 单职责**：一个 PR 只解决一件事；混入无关变更（生成脚本的杂散 diff）必须精准剔除，只保留目标文件

## 回归判定铁律（最重要）

判定"某行为是不是我引入的回归"之前，**必须**先对照上游基线：

```bash
git show <上游基线commit>:<文件路径>   # 看原始行为
```

- 基线本来就这样 → 不是回归，是上游既有行为，调整测试预期即可
- 基线没有该行为 → 才是你的改动引入，需修复
- **证据链未闭环时，严禁执行关 PR、强推、reset --hard 等不可逆操作**

## 回复维护者评审

1. 收到评审意见后：先在原 PR 确认收到，再按意见调整代码、测试、spec、changelog、PR 正文，**全部同步改**
2. 维护者若要求收敛能力范围（如砍掉某枚举档）：照做，保持与小程序/Web 端对齐是常见理由
3. 调整后在 PR 下回复说明改动点，并 @ 维护者
4. 全量回归后再推：调整后必须跑组件全量测试 + 周边组件基线对照，确认无新回归

## 测试与验证规范

1. **断言先读实现再写数值**：测试断言的数值（高度、offset、耗时）必须来自实际实现行为，不凭空估计
2. **新增公开 API 必须补测试**：正常路径 + 边界（RTL/errorText/主题切换/兼容模式）至少各一
3. **真机验证优先**：涉及 UI/性能的改动，用真机（如 OPPO PFEM10）跑 demo 取证；性能对比需同口径（同设备、同构建模式、同数据量），Debug JIT 冷启动与热态重建不可直接混比
4. **性能采样自动化**：手动 adb tap 坐标点击误差大且反复出错；改用 `--dart-define` 参数化启动 + 程序化滚动（ScrollController.animateTo）+ logcat 输出结果，一次到位
5. **本地 golden 失败需甄别**：存量 golden 失败（如本地环境 97 个）是环境差异，与本次改动无关的不算回归

## 常见坑速查

| 坑 | 正确做法 |
|---|---|
| fork 历史分叉带着提 PR | 强制同步上游后重放提交，保持零差异 |
| 生成脚本混入无关变更 | 只 commit 目标文件，`git add` 精准指定 |
| 删 PR 模板/勾选清单 | 原样保留模板 HTML 注释 |
| 性能数据口径不一 | 固定设备+构建模式+数据量，写明测量环境 |
| 判定回归不查基线 | `git show <基线>:<文件>` 先行 |
| 老旧 issue 不验证就认领 | 先在上游最新 develop 验证是否仍存在 |
| adb 手动坐标点击 | 程序化脚本采样，避免 UI 误触 |
| 方案未确认就开发 | 等 `Received` + 维护者方案确认 |

## 提交信息格式

```
<type>(<scope>): <一句话概括> (#issue号)

<问题背景 2-3 行>

方案：<核心改动点列表>

验证：
- 测试结果（N/N 通过）
- 真机/性能数据（如有）

后续说明（是否建 PR、等待确认等）
```

type 取值：feat / fix / perf / refactor / test / docs / chore
